# 首次接入：先准备 Bot、组织和私聊入口

本文件供安装 Agent 执行。业务人员只需说明要服务的企业和业务能力；Bot 名称或配置能在本机确认时，由 Agent 查询，不让业务人员抄 ID、链接、Secret 或命令。首次接入可由 Agent 操作界面；以后的定时续期必须由脚本独立完成。

**首次设备没有 Bot 私聊、没有续期链接是正常初始状态。此时不运行历史搜索，也不运行定时续期。** 按下面顺序建立入口。

## 1. 先确定本机要维护的 Bot

先读本机业务服务已明确使用的 CLI/profile 路径，再盘点；服务实际指定的 profile 比终端默认值更能说明业务目标。不要为找配置读取 Secret/凭据文件，也不要修改业务服务。

先查已知 CLI profile：`delivery/profiles.py` 只调用官方接口，原始身份存到包外私有文件。正确身份命令是 `wecom-cli identity whoami`，不是 `wecom-cli whoami`。`auth show --status` 的 authorized 只表示 CLI 已绑定，不代表业务权限未过期。

**已绑定的设备先从现有 CLI 获取入口，不要要求重新扫码。** 已确定业务 profile 后运行（省略 `--profile` 表示默认配置；自定义配置使用已经查明的绝对路径）：

```bash
python3 delivery/existing_entry.py --cli /absolute/path/wecom-cli --node /absolute/path/node --profile /absolute/existing/profile --output /absolute/private/existing-entry.json
```

工具检查版本、绑定状态和 Bot 身份，执行只读 `message aibot sessions list`。若返回 `850003`，从当次官方 `help_message` 提取续期链接，查询后再次核对绑定未变。身份、过期证据与原链接只写入新的私有报告，不输出会话正文、不读凭据、不调用 `auth init`、不发送消息。CLI 已绑定但权限过期、桌面昵称不同、暂时找不到 Bot 或私聊，都不是重新绑定的理由。不要新建 profile 来绕开定位问题。

将报告的 `cli_bot_id` 和 `authorization_url` 用于后续草稿，**原链接逐字保留**，包括 `type`、`for_native`、窗口参数和编码；不自行重组为固定 `type=1`。工具未取得链接时报告 `official_authorization_url_unavailable`，保留已有绑定，继续只读核对官方资料入口；健康消息权限不一定返回链接，不得通过写操作制造错误。取得链接仅证明 CLI 目标，组织、当前桌面身份和私聊仍需核验。

| 设备状态 | Agent 应做什么 |
| --- | --- |
| 业务目标与已有 CLI Bot 一致 | 复用该 profile；继续确认所属组织。不要重建 Bot 或覆盖凭据。 |
| 有多个组织或多个 CLI profile | 列出本机查到的企业/Bot 候选，结合业务目标选定；不要默认取第一个 profile，也不要把同名当成同一身份。 |
| 确认目标 Bot 没有已有 CLI 绑定，且用户明确要求首次接入 | 另行完成官方接入；保留其他 Bot 配置。不能因为暂时没有定位到现有 Bot，就擅自进入扫码分支。 |
| 没有可用 Bot | 帮用户在目标企业的官方机器人入口创建或接入一个 Bot。确认新权限范围后再操作；没有创建权限时明确需要该企业提供 Bot/名片，不能拿另一个企业的 Bot 凑数。 |

首次创建、首次绑定、首次授予业务权限与“续期已有权限”分开记录。工具不能替没有权限的成员创建企业资源，不能扩大权限来让验收变绿。CLI profile、Bot、所属组织确认后，同一轮安装不再反复问用户“用哪个 Bot”。

## 2. 确认组织与 Bot 身份，先不依赖聊天记录

还没有 Bot 配置时也能诊断当前界面，不需要编造 ID。先在界面打开企业菜单或通讯录 Bot 列表，再使用本版本实际执行 Python：

```bash
.venv/bin/python delivery/gui.py --action inspect-expanded --python "$PWD/.venv/bin/python3" --evidence-dir "$HOME/.local/state/wecom-auth-keeper/setup-inspect-1"
```

这是同用户 GUI launchd 的只读临时任务；`--python` 只用于无配置的 inspect/inspect-expanded，不能用于续期或覆盖配置中的执行主体。它读取当前可见的原生组织菜单、通讯录 Bot 名称候选和页面标志，不导航、不发送、不授权、不读取凭据。未打开企业菜单时，菜单结果为空不代表没有组织；未展开/滚动完整列表时不能排除未显示的 Bot。结果保存在包外本机私有目录。

1. 在企业微信原生企业菜单读取准确名称及选中标记。业务企业全称与菜单简称分别保存；不要用头像、人名、聊天里提到的企业名判断当前组织。
2. 切到目标组织，从“机器人”目录、通讯录中的机器人或已知 Bot 名片打开详情。5.0.13 门户中应优先查看“查看更多机器人”或现有机器人卡片；“查看更多机器人”实际跳到通讯录的“智能机器人”分组，侧栏可能选中“更多”，不是“我的机器人”管理卡片页。读取分组下的 Bot 行（包括“企业创建的”），按需展开/滚动，不能拿卡片尺寸筛选通讯录列表。不要只看“管理机器人”。能管理的 Bot 可走“管理机器人”；管理列表不包含所有可使用 Bot，列表空不代表 Bot 不存在。
3. 打开候选 Bot 的官方“可使用权限”页；如果资料页没有权限入口，可先从带原生 Bot 标记的通讯录行进入空私聊，再打开聊天中的机器人资料/权限入口。这属于只读定位，身份匹配前不发送消息、不授权、不保存为已通过目标。将 URL 的 `aibotid`、`str_aibotid` 与选定 CLI/官方链接核对。两个组织中的 Bot 分别处理。名称可能变更，最终绑定依靠身份；没有匹配时不改 CLI 去迁就当前页面。
4. CLI授权真人与当前组织显示名不同时，可能是组织别名；用既有 CLI 的官方身份和该原链接打开后的页面提示核验。不能仅凭名字差异断言不同账号，不通过新扫码“证明”身份，也不能拿另一 Bot 的权限页冒充当前 CLI 的续期证据。
5. 保存本机映射：CLI profile → Bot 双 ID → 当前 Bot 显示名 → 业务企业名称 → 原生企业菜单准确名称 → 需要维护的权限。原始 ID/URL 只存私有配置。

5.0.13 可能恢复上次机器人子页面：先辨认“智能机器人”门户、“我的机器人”列表、“机器人详情”或权限弹窗，再决定下一步。切页后原生 AX 树可能需要重新请求展开；单纯保持 AXEnhancedUserInterface=true 不证明新树可读。`inspect-expanded` 是诊断手段，不能把搜索框里自己输入的 Bot 名称当作已找到 Bot。Bridge 的组织接口返回 success/缓存当前组织也不代替原生选中标记。

通讯录中的 Bot 行可能先打开“机器人资料”，管理列表则可能打开“机器人详情”；按实际页面辨认“发消息/去使用”和“可使用权限”，不要把两条路径混成一个模板。加载等待必须等待明确的新页面标志或可读列表，不能把 unknown 当成完成条件；结构未识别不等于列表为空。

部分组织的门户没有“查看更多机器人”，此时从侧栏 **更多 → 通讯录 → 智能机器人** 进入目录。首次接入由安装 Agent 按实际界面操作；不同组织侧栏项目数量和位置可变，“更多”也可能在功能列表外，不能套固定行号或遍历邮件、日程等无关功能。展开菜单后重新读取“通讯录”项，菜单消失时先重新定位。分组折叠、列表仅当前可见或一次滚动内容未变，都不能据此声明 Bot 不存在。只记录明确读到的候选与仍未知的范围。

没有私聊时，不要遍历企业反复搜索 `authorizationList`；还没有发过的链接不可能从历史里找到。

找不到同名 Bot 时，不要立即判断不存在或让用户重新选 Bot。先核对目录范围与业务服务使用的 profile；候选数量有限时，可只读查看官方资料/权限页排除改名，最终以身份匹配为准。若仍不能把现有 CLI Bot 对应到当前桌面可用 Bot，保留“组织/桌面身份未核验”状态，并记录具体页面/官方错误证据。不要无休止换入口、换绑原配置或擅自另建 Bot。已有业务目标明确时，不重复问“选哪个 Bot”，也不让用户寻找技术 ID。

### 已有官方链接，但还没找到 Bot 私聊

不要把“必须先找到 Bot 私聊”变成无法诊断身份的循环。先复用本机已有的准确官方链接；若原生资料入口不可达，在用户授权的诊断范围内，可将原链接临时放入**已确认属于当前账号的“自己”会话**，用于打开只读页面。需核对本人资料与进入路径，不能只凭同名标题，也不能发送给他人、群或另一 Bot。不默认采用这种载体作为正式续期入口，不据此签发私聊入口回执。

写入时先保留已有草稿，逐字核对输入值与原链接一致，再核验接收会话和焦点后发送一次并读回；远程键盘可能丢失 `?`、`_` 等字符，不应重复盲打。消息既已存在就复用。用绑定双 ID 的页读取结果并关闭；`open -a` 返回0、出现 AXWebArea 或只有“可使用权限”标题都不代表内容加载完成。等待可读权限行或明确官方错误，不因空白重建 CLI。

官方页出现“暂无法授权，仅限机器人创建者可进行授权”时，脚本返回 `authorization_creator_required`；“当前账号非机器人所属企业”对应 `authorization_organization_mismatch`；“机器人已删除”对应 `authorization_bot_deleted`。这三项与过期、导航失败分别处理。先核对原生组织选中项，在已有业务目标范围内有界验证正确组织；仍受限时，保留 CLI，由 Bot 创建者使用具备权限的桌面身份/设备完成安装。**不通过换绑、扫码新建 profile、点击其他 Bot 或修改客户端权限来绕过官方身份限制。** 未实测的组织保留 unknown，不能仅凭昵称判定账号不符。

如果错误页显示创建者姓名，可从该**已绑定页面内唯一可核验的资料入口**只读查看创建者组织/部门线索；姓名可能是分段AXStaticText并带AXPress，不能因整句不同漏掉限制。只读所需身份线索，不点“发消息/添加联系人/编辑”，关闭本轮资料浮层和权限页并确认主窗口保留。组织名称或部门路径只是定位线索，不能冒充企业ID匹配。CLI绑定证明API身份，桌面登录态证明UI身份；两者必须具备对应权限。已有其他桌面服务时，不擅自切换登录账号来通过测试。

`inspect-expanded` 可只读报告当前官方页的 `blocking_error`，无配置时不能证明它属于选定 CLI。具有正确配置时的 `check-existing`/入口核验/维护都会检查绑定页错误；入口核验失败仍自动关页，不写成功回执。诊断结束后，回到已核验 Bot 私聊准备正式入口，再单独验续期与定时。

## 3. 从已核验 Bot 建立私聊，准备一次入口

1. 关闭权限页，回到同一 Bot 详情，使用“去使用”“发消息”或客户端等价的单聊入口（若第2步已由该资料页进入并完成身份核验，则复用这个会话），建立**本机当前账号与这个 Bot 的私聊**。不通过建群完成，不用文件传输助手、其他人的私聊或另一设备的历史代替。
2. 安装 Agent 核对进入路径与聊天类型。仅名称匹配不证明是私聊；不要在同名群里发送链接。无法从已核验详情进入时先修正该步骤。
3. 根据已核验的 CLI Bot ID、官方授权 URL、业务权限和组织，用 `onboard.py --input <私有输入.json> --output <私有配置.json>` 生成草稿。输入增加可选 `organization_selector_name`，填写刚刚实际读到的原生菜单名；`organization_name` 保留业务企业名称。此时返回 `entry_preparation_required`，不是安装成功。
4. 生成准备发送的文本（只落盘，不发送）：

```bash
python3 delivery/prepare_entry.py --config /absolute/private/config.json --message-output /absolute/private/renewal-entry.txt
```

文本包含固定标记 `【自动续期入口】` 和本 Bot 的官方链接。先看该私聊是否已经有匹配双 ID 的入口；有则复用，无则按用户对本次安装的授权**只发一次**。发送由登录的业务账号在已核验 Bot 私聊内完成；不依赖当前可能已过期的 Bot“发送消息”API权限。没有发送授权时，把具体目标和文本准备好后一次确认，不问抽象“能否继续”。

5. 在本机私聊中确认消息已送出且链接完整可读，再打开链接核对同一 Bot 官方权限页。发送请求成功、另一个设备收到或 Agent 口头说已发送均不够。记录这是“新建私聊并发送入口”还是“复用已核验入口”，关闭权限页。

这条链接是长期可查找的导航入口，不是每次续期新发一条消息。不要把 Bot Secret、token 或账号密码放进消息。入口链接/ID 不进入分发 ZIP 或群内验收报告。

## 4. 离开当前会话，再验入口能否自动找回

安装 Agent 先切到另一个普通会话或另一个企业，关闭所有本轮权限页，再执行：

```bash
.venv/bin/python delivery/gui.py --config /absolute/private/config.json --action entry-verify --evidence-dir /absolute/private/entry-check-1
```

脚本使用 GUI launchd 的真实 Python，核对当前 CLI profile、原生企业选中项，从聊天历史找到双 ID 匹配链接，打开匹配的权限页、读取全部配置权限并自动关页，再核对原生组织。它不发送消息、不授权、不改变 Bridge，也不安装服务。目标页已打开或同企业目标会话仍在前台时返回 `bootstrap_cold_start_required`，不能用预先打开页面冒充自动找回。

成功后保存本设备、当前配置绑定的 `entry_receipt`，并启用已核验的组织适配器。该回执证明脚本能够找回入口；**私聊类型须由安装 Agent 在第3步从 Bot 详情进入时确认**，脚本不会把“聊天标题相同”说成私聊类型已验证。把这项观察及来源记入验收记录。换 Bot/profile/组织/权限范围/Python、CLI、Node 路径或复制配置到其他设备后，需要重新核验。

新生成的草稿缺少有效入口回执时，维护命令和定时任务生成器返回 `bootstrap_incomplete`，不会进入授权步骤。旧有生产配置不自动迁移；对旧设备升级时按此流程建立新版本私有配置，保留旧状态与回滚路径。

如果找回了正确页面，但所选权限只有“授权”按钮、没有有效期，返回 `bootstrap_authorization_baseline_required` 并关闭权限页，保留“入口已找到”的诊断。这个界面不能单独区分从未授权与已经过期；不能把它当导航失败，也不能据此静默新增权限。安装 Agent 先核对既有授权证据；新权限须完成用户确认范围内的一次首次授权，再重新运行入口核验建立有效期基线。基线具备后，后续周期才按已配置范围自动续期。

## 5. 最后才验续期和定时运行

入口验收只算“安装准备完成”。按照 AGENT-INSTALL.md 继续验证真实续期、前后有效期、关闭页面、必要的只读业务检查，再验证实际定时触发。首次需要授予的权限不能伪装成续期；没有实际到期日延长不能写“续期通过”。共用桌面的 Bridge 协调问题属于运行阶段，入口准备完成也不能消除它。

| 现象 | 回到哪一步 |
| --- | --- |
| 没有 Bot / CLI unauthorized | 第1步，完成创建或官方绑定。 |
| 找不到组织 / 页面不属于 CLI Bot | 第2步，核对原生组织与 Bot 身份；不改凭据凑数。 |
| 新设备搜不到 Bot 聊天 | 第3步，从 Bot 详情建立私聊；不重跑历史搜索。 |
| 私聊存在但没有 authorizationList 链接 | 第3步，发一次本机正确入口并读回。 |
| 已有入口但后台找不回来 | 第4步，检查导航/版本/实际 Python 系统权限，不重复发消息。 |
| 权限显示从未授权 | 完成用户确认范围内的首次授权，单独记录，再验续期。 |
| entry-verify 通过，maintain 仍失败 | 排查具体运行阶段，保留入口成果；不重建 Bot、不重置 CLI。 |
