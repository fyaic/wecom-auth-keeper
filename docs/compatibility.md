## 历史入口的跨设备部署说明

1. 备份当前代码提交、配置与服务启动文件，确认目标 Bot 和能力白名单。
2. 旧聊天导航需要已经存在的身份匹配官方链接。标准分发首次没有私聊/链接时，由安装Agent按 FIRST-RUN.md 建立；不让业务人员自行准备技术配置，也不反复搜索不存在的历史。
3. 在 Keeper 配置设 `chat_history_navigation: true`，确认 `bot_chat_name` 是完整会话名。先运行不带 `--existing-window` 的 `--check` 验证导航。
4. 使用 Gateway 调度时，同时更新支持周期清理的 Gateway 代码，设置 `WECOM_AUTH_KEEPER_EXISTING_WINDOW_ONLY=false`、`WECOM_AUTH_MAINTENANCE_PRE_RENEW=true`、`WECOM_AUTH_KEEPER_WITHIN_HOURS=24`。需要关页时设 `WECOM_AUTH_KEEPER_CLOSE_WINDOW=true`；旧 Keeper 不支持关页命令，不可单独开启这个选项。
5. 在同一 launchd 启动链验证，而非仅从终端运行。验证页面身份、有效期延长、pending 清除和关页结果，并用同一 Bot 的业务探针独立确认。

中文原生聊天界面、已登录解锁的桌面和后台 Python 的辅助功能授权是前提。运行期间仍会切换会话与前台；完成后关闭权限页不等于恢复原聊天、关闭聊天记录面板或实现多个 UI 服务互斥。其他 UI 服务需要共享桌面锁或错开执行；本项目只协调使用 `~/.wecom-auth-renew/desktop.lock` 的 Keeper 进程。锁屏、强制杀进程或客户端卡死时不能保证清理完成。

旧记录中的独立 `maintain.py` 启动链曾被辅助功能检查拒绝，见[历史验收](validation.md)。本分支后续本机和远端结果分别保存在[分发验收记录](../delivery/VALIDATION.md)，不要把某次本机成功推广到其他设备；远端完整验收未通过前仍为内部候选。

## 验证由谁执行

正式任务是 launchd → Gateway 的确定性 TypeScript 调度脚本 → Keeper Python/PyObjC AX 脚本，不调用 Codex、模型、视觉识别或 computer-use 服务。Codex 在开发阶段修改代码、准备测试并读取证据；成功的后台周期没有 Codex 中途点击、补导航或批准授权。早先的代理手动恢复、首次脚本失败和修复后的纯脚本成功在[验证记录](validation.md)中分开陈述。
